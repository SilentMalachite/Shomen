## フェーズ 2 — フォームとセッション

作るもの:

- `form` POST の Input 束縛（urlencoded）
- 検証エラー時に同じフォームを 422 で描画できること
- 署名セッションクッキー
- CSRF: セッションに紐づくトークン。POST で不一致なら 403
- `input` のコンパイル時ラベル検査（同一ビュー内の `for` / ラップ、または `aria-label`）。フェーズ 1 は `input` 要素を出すだけで、この検査はしない

受入:

- フォームを 1 つ持つ example が、投稿後に値を再表示できる
- CSRF 無し POST が 403
- セッションが無い応答に Set-Cookie が付く

## フェーズ 3 — コマンドとイベントと SQLite

作るもの:

- Command / Event の型
- 仕様 7 の `events` テーブル（ストリーム、版、ストリームをまたぐ `id`）を持つ SQLite 追記ストア
- ストリームのいまの版以外への追記は `Shomen::Conflict` を投げる。捕まえられなければ、サーバは 409 の HTML を返す
- チェックポイントを持つメモリ上のプロジェクション。ビューが読む前に追いつく
- 起動時リードモデル再構築
- example: 名前を変更してイベントが 1 行増える

受入:

- 同じコマンドを 2 回扱うと events が 2 行（上書きではない）
- 再起動後もリードモデルが復元される
- 1 つのストリームに同じ期待版で 2 回追記すると、片方は成功し、もう片方は `Shomen::Conflict` を投げて行を増やさない
- ストリームより先の版を期待する追記は、`Shomen::Conflict` を投げて行を増やさない
- 1 つの SQLite ファイルを 2 つのプロセスで使うと、両方からの追記が一方を待たせて成功し、一方のプロジェクションは、追いついた後に他方が追記したイベントを見る
- 1 つのプロセスの多数のファイバーが同時に 1 つの SQLite ファイルへ追記しても、すべて成功する
- Store が HTML を import していない
- コマンド、イベント、プロジェクションが SQLite の名前を出さない

## フェーズ 6 — Postgres と本番寄せ

作るもの:

- Store の Postgres アダプタ。追記を直列にし、id が順に見えるようにする
- `SHOMEN_ENV=production` で例外本文を隠す
- 最低限の CSP
- `SHOMEN_ENV=production` では 32 バイト以上の `SHOMEN_SECRET` を必須にする
- 鍵を替えるための `SHOMEN_SECRET_VERIFY`
- `Shomen::Server.start` の `reuse_port`
- SIGTERM と SIGINT でのグレースフルシャットダウン

受入:

- SQLite と Postgres を同じ Command API で使える
- example の既定は SQLite のまま
- `SHOMEN_ENV=production` で `SHOMEN_SECRET` が無いと、変数名を含むメッセージを出して起動に失敗する
- `SHOMEN_SECRET_VERIFY` で署名したクッキーと CSRF トークンが通り、応答はクッキーを `SHOMEN_SECRET` で出し直す
- 同じ鍵の 2 プロセスを 1 つの Postgres DB につなぐと、一方が描画したフォームを他方へ投稿しても通り、どちらへの GET も変更を表示する
- 1 つの追記トランザクションが挿入後に開いたままの間、別のプロセスからの追記は、先の方がコミットするまで待つ
- 2 プロセスから同時に追記しても、チェックポイントをたどるプロジェクションはすべてのイベントを `id` 順に 1 回ずつ受け取る
- SIGTERM の後、処理中の要求（SSE ストリームを除く）は `Connection: close` 付きの通常の応答で終わり、待機中のキープアライブ接続は閉じられ、新しい接続は拒まれ、プロセスは上限時間内に終了する

---

## フェーズ 7 — スケールアウト

作るもの:

- コンシューマ: 要求の外で動くプロジェクションと反応。チェックポイントを保存し、別のプロセスがチェックポイントを動かしていないときだけバッチをコミットし、失敗したら間隔を伸ばして再試行する
- 行とチェックポイントを DB の表に置くプロジェクションと、ある `id` を見る必要がある要求の上限つきの待ち
- 追記後の通知（Postgres の `LISTEN/NOTIFY`）と、予備のポーリング
- どのプロセスで追記された変更も受け取る SSE ストリーム
- GET ルートの検証子、ビルド ID、セッションの CSRF トークンから作る弱い `ETag` と、`If-None-Match` が一致したときの 304
- 描画した断片の、プロセス内の上限つきキャッシュ（キーは入力、見る人によって中身が変わるなら見る人、表示するデータとともに変わる値）
- Postgres replica からの読み取りと、セッション内の read-your-writes

受入:

- 2 プロセスで同じコンシューマを動かすと、各イベントの DB への効果は `id` 順に 1 回だけ適用される。バッチの途中で一方のプロセスを殺すと、他方が保存済みのチェックポイントから続け、イベントを落とさない
- コンシューマの DB への書き込みとチェックポイントは一緒にコミットされる。その間で失敗すると、どちらも残らない
- プロセス A につないだ SSE クライアントが、プロセス B で追記したイベントの更新を受け取る
- `If-None-Match` が一致する GET は 304 を返し、ビューを呼ばない
- セッションかビルドが変わった後は、古い `ETag` を付けた GET に 200 の完全な応答を返す
- いまの CSRF トークンを含む断片をキャッシュしようとすると例外になる
- replica が遅れていても、1 つのセッションの POST、そのリダイレクト、続く GET は追記した変更を表示する
- 表に置いたプロジェクションが上限時間内に必要な `id` へ届かなければ、古い状態ではなく 503 を返す。セッションがその `id` を忘れた後は、同じページが 200 を返す
- SQLite のアプリは変更なしで動く。このフェーズのどの機能も、DB 以外の裏側のサービスを必要としない
