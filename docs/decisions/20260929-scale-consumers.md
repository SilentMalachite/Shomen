# 状況

Rails は ActiveJob と Solid Queue などで、要求の外で動く処理を持つ。Shomen の仕様には、要求の外で動く処理が無い。メール送信や重い集計を要求の中で行うと、応答が遅れ、失敗したときに要求ごと失敗する。複数のプロセスが同じ処理を動かすと、同じイベントを二重に処理しかねない。

# 決定

フェーズ 7 でコンシューマを足す。コンシューマは要求の外で動くプロジェクションまたは反応で、名前とチェックポイントを持つ。チェックポイントは `consumers(name TEXT PRIMARY KEY, checkpoint INTEGER NOT NULL)`（Postgres では `BIGINT`）に置く。

コンシューマはイベントをバッチで処理する。バッチは、DB への書き込みと新しいチェックポイントを 1 トランザクションでコミットする。コミットするのは、先に別のプロセスがチェックポイントを動かしていないときだけにする。

Postgres では、バッチ全体を 1 つのトランザクションにする。

1. `SELECT … FOR UPDATE SKIP LOCKED` で自分の行をロックする。行が返らなければ、別のプロセスが処理中なので何もしない
2. チェックポイントを読み、その後のイベントを適用する（副作用を含む）
3. 新しいチェックポイントを書き、コミットする

ホストごと落ちたときのロックは、`idle_in_transaction_session_timeout`（既定 60 秒）で外れる。1 回の副作用は、この上限より短く終える。これは文と文の間の空きを制限するもので、バッチ全体の長さは制限しない。全体の上限が要るときは、Postgres 17 以降の `transaction_timeout` を使う。

SQLite では、書き込みトランザクションの中で副作用を実行しない（`20260929-scale-sqlite-writes.md`）。

1. トランザクションの外でチェックポイントとその後のイベントを読み、副作用を実行する
2. `BEGIN IMMEDIATE` で短いトランザクションを始め、DB への書き込みを行う
3. `UPDATE consumers SET checkpoint = 新しい値 WHERE name = … AND checkpoint = 読んだ値` を実行する。1 行も更新されなければ巻き戻す

DB の外への副作用（メール、HTTP 呼び出し）は少なくとも 1 回実行されるので、反応は繰り返しに耐える作りにする。失敗したイベントは飛ばさず、間隔を伸ばしながら再試行する。1 つのコンシューマが止まっても、ほかのコンシューマは進む。予約実行と遅延実行（何時間後に送る、など）は、このフェーズに入れない。

# 理由

Postgres の行ロックはトランザクションに結びつくので、ロックを持つ者と書き込む者が必ず同じになる。行ロックは、ほかの追記やほかのコンシューマを止めない。プロセスが死ぬとトランザクションは巻き戻り、ロックも外れる。SQLite のロックは DB 全体に及ぶので、副作用の間持ち続けることはできない。そこで、チェックポイントを比べて書き換えることで、二重の適用を防ぐ。2 つのプロセスが同時に動くと副作用が二度起きうるが、副作用はもともと少なくとも 1 回の約束である。イベントは追記のみで `id` 順に読めるので、キューの表を別に持たなくても、イベントそのものが仕事の一覧になる。

# 破棄した案

- 専用の接続でセッション単位のアドバイザリロックを取り、リースにする（接続が気づかないうちに切れるとロックが外れ、持ち主が知らないまま 2 つ目が動く。ホストが落ちると、TCP の keepalive が諦めるまでロックが残る）
- SQLite でも、副作用を含むバッチ全体を 1 つの書き込みトランザクションにする
- Solid Queue のように仕事を行として入れ、`FOR UPDATE SKIP LOCKED` で取り出す表を持つ
- Redis などの外部キューを使う
- 失敗したイベントを飛ばして先へ進む
