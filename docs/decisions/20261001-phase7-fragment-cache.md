# 状況

仕様 10 と `20260929-scale-fragment-cache.md` は、描画した断片をプロセス内の上限つきキャッシュ（LRU）に置き、キーに断片が依存するものをすべて含め、いまの CSRF トークンを含む断片をキャッシュしようとしたら例外にすると決めた。API、上限の数え方、キーの組み立て、トークンの確かめ方は決めていない。2026-10-01 にユーザーは、上限をバイト数で数えると決めた（`docs/superpowers/plans/2026-10-01-phase7-overview.md`）。

# 決定

- `Shomen::FragmentCache.new(max_bytes : Int32 = 16 * 1024 * 1024)`。`max_bytes` が正でなければ `ArgumentError`。アプリは定数に 1 つ置き、プロセスの全セッションが共有する
- `Shomen::Route#cached(cache, name : String, *key, & : -> Shomen::Fragment) : Shomen::Fragment`。`name` は断片の名前、`key` は入力、見る人、データとともに変わる値で、0 個でもよい。`key` の値が `String`、`Int32`、`Int64` でなければコンパイルエラー。キーの各値は、文字列か整数かの別と長さを前に付けてつなぐ。`Int32` と `Int64` の同じ数は同じキーになる
- キャッシュに無ければブロックを呼んで描画し、`Shomen::FragmentCache#fetch(key, csrf_token)` がルートの `csrf_token` を含むか確かめる。含めば `ArgumentError` を投げ、キャッシュに置かない。`csrf_token` が空なら確かめない。キャッシュにあればブロックを呼ばない
- 戻り値は描画済みの HTML を持つ `Shomen::CachedFragment`。ビューの `embed` と `render_fragment` にそのまま渡せる
- 大きさは、キーと HTML のバイト数の和で数える。和が `max_bytes` を超えたら、最も長く使われていない断片から捨てる。1 つで `max_bytes` を超える断片は置かない
- 描画はキャッシュのロックの外で行う。同じキーを同時に描画したら、後に終わった方が残る

# 理由

ルートのメソッドにすれば、ルートが持つ CSRF トークンを毎回渡せ、アプリがトークンを渡し忘れることが無い。キーの値を `String`、`Int32`、`Int64` に絞るのは、`Input` の型と同じで、`to_s` が番地を含む値をキーに入れる誤りをコンパイル時に止めるためである。文字列か整数かの別と長さを前に付ければ、`"a", "bc"` と `"ab", "c"`、`"1"` と `1` が別のキーになる。整数の幅は表示に関わらないので、`1` と `1_i64` は分けない。

キャッシュにあった断片は、置いたときにそのセッションのトークンを含まないと確かめてある。トークンはセッションごとに違うので、あとから来た別のセッションのトークンを含むことは無い。

バイト数で数えれば、大きな断片が多くてもメモリの上限が決まる。Crystal のオブジェクトの付帯分は数えないので、実際のメモリは少し多い。描画をロックの外で行えば、遅い描画が別のキーの読み出しを止めない。

# 破棄した案

- 件数で上限を決める（1 つの大きさでメモリが変わる）
- ビューの中でキャッシュを使う（ビューは CSRF トークンを知らない）
- キーを任意の値にする（`to_s` が番地を含む値で、キャッシュが当たらないままメモリを使う）
- 描画をロックの中で行う（遅い描画がすべての読み出しを止める）
