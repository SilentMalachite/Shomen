# 状況

アーキテクチャ文書は、リードモデルを起動時にメモリで作り直すとしていた。この形では、別のプロセスが追記したイベントが見えない。1 プロセスでも、起動時間とメモリがイベント数に比例して増える。

# 決定

プロジェクションは、最後に適用したイベントの `id` をチェックポイントとして持つ。`id` 順に、チェックポイントより後のイベントだけを適用する。フェーズ 3 ではメモリ上に置き、起動時はチェックポイント 0 から始め、ビューが読む前に追いつかせる。フェーズ 7 で、行とチェックポイントを DB の表に置けるようにする。表に置いたものはコンシューマだけが更新し、読む側は待つ（`20260929-scale-read-your-writes.md`）。

この方式は、`id` N まで読んだ読み手が、後から N 以下の新しいイベントを見つけないことを前提にする（`20260929-scale-event-order.md`）。

# 理由

チェックポイントがあれば、どのプロセスも同じイベントログから同じ順で追いつける。別のプロセスが追記したイベントも、次に読む前に取り込める。読む前の追いつきは、差分が無ければ主キーの範囲検索 1 回で終わる。フェーズ 3 のうちにこの形にしておけば、フェーズ 6 と 7 でコマンドとプロジェクションのコードを変えずに済む。

# 破棄した案

- 起動時の全件再構築だけを残し、スナップショットで速くする
- プロジェクションを通知だけで更新し、読む前には追いつかない
