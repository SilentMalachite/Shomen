# 状況

SQLite の書き手は一度に 1 つである。書き込み中に別の書き手が来ると、ビジータイムアウトの間、待ってから再試行する。`crystal-sqlite3` はこれを `PRAGMA busy_timeout` で行い、SQLite はその間 OS のスレッドを眠らせる。Crystal は 1 スレッドで多数のファイバーを動かす。あるファイバーがロックを待って眠ると、ロックを持つファイバーも動けず、タイムアウトまでコミットできない。

# 決定

SQLite アダプタの書き込みは、次のようにする。

- 追記とコンシューマの書き込みは `BEGIN IMMEDIATE` で始める
- プロセス内では、1 つのファイルへの書き込みの前に、ファイバーが待てるプロセス全体のロック（標準の `Mutex`）を取る。同じファイルを開いたストアが複数あっても、ロックは 1 つにする
- プロセスをまたぐ待ちは、ビジータイムアウト（既定 5 秒）に任せる
- 書き込みトランザクションの中では、副作用（メール、HTTP 呼び出しなど）を実行しない

# 理由

ファイバーが待てるロックで先に並ばせれば、SQLite のビジー待ちに入るのは別のプロセスと競ったときだけになる。ビジー待ちでスレッドが眠っている間に待たされるのは、別のプロセスが持つロックなので、デッドロックにはならない。ただし、その間はプロセス全体が止まり、ほかの要求も最長でタイムアウトまで待たされる。複数のプロセスで 1 つの SQLite ファイルに書く構成は、この止まりを受け入れられる規模に限り、それを超えたら Postgres に移る。SQLite のロックは DB 全体に及ぶので、書き込みトランザクションの中で副作用を待つと、その間すべての追記と、ほかのコンシューマが止まる。

# 破棄した案

- ビジータイムアウトだけに任せる
- ストアごとにロックを持つ（同じファイルを開いた 2 つのストアが、同じプロセスの中でビジー待ちに入る）
- 書き込み専用のファイバーを 1 つ置き、書き込みをチャネルで渡す（ロックより仕組みが大きい）
