# 状況

仕様 6 は、セッション Cookie `shomen_session` の値を署名すること、中身を小さなキーと値の map にすること、最初のサーバ側ストアをメモリにしてよいことを定めている。フェーズ 2 でセッションに結びつける値は CSRF トークンだけである。

当初はメモリ上の map を `id` ごとに持ち、CSRF トークンをそこに入れていた。最終レビューで、Cookie を持たない要求（404、ヘルスチェック、クローラ）のたびに map の項目が増え、消えないことがわかった。長く動くサーバではメモリが増え続ける。

# 決定

Cookie の値は `<id>.<署名>` とする。`id` は `Random::Secure.hex(32)`、署名は `SHOMEN_SECRET` を鍵にした `id` の HMAC-SHA256 を 16 進で表したもの。CSRF トークンは保存せず、同じ鍵で `"csrf:" + id` の HMAC-SHA256 を 16 進で表したものを毎回計算する。`Shomen::SessionStore` はサーバ側に状態を持たない。署名が合わない、または形が壊れているときは新しいセッションを作り、その応答に `Set-Cookie` を付ける。署名が正しければ、同じ `SHOMEN_SECRET` で再起動した後でも同じセッションとして扱う。署名は `OpenSSL::HMAC`、比較は `Crypto::Subtle.constant_time_compare` を使う。どちらも標準ライブラリである。

map をサーバ側に置くのは、ルートがセッションへ値を書く API を入れるときにする。そのとき、上限と期限もあわせて決める。フェーズ 2 にその API は無い（`20260929-phase2-route-csrf-token.md`）。

# 理由

フェーズ 2 で map に入れるものは、`id` と鍵から導ける値だけである。保存しなければ、要求がいくら来てもメモリは増えない。`"csrf:"` を前に付けるので、トークンが Cookie の署名と同じ値になることはない。`id` は 16 進だけなので、`"csrf:" + id` が別の `id` と一致することもない。Cookie は HttpOnly なので、ページ内のスクリプトが `id` を読んでトークンを計算することはできない。

# 破棄した案

- メモリ上の map に `id` ごとの CSRF トークンを保存する（当初の決定）。Cookie の無い要求のたびに項目が増え、上限も期限も無いのでメモリが増え続ける
- 保存したまま、ストアに件数の上限や期限を付ける。書き込む値が無いフェーズ 2 では、仕組みを足しても得るものが無い
- map を JSON にして Cookie に入れ、全体に署名する
- 署名せず、推測できない `id` だけに頼る
