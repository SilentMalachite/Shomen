# 状況

Rails は、ETag による条件付き GET で描画と転送を省く。Shomen の応答には、`ETag` も `Cache-Control` も無い。Shomen のページは、セッションから導いた CSRF トークンを含み、デプロイでマークアップが変わる。

# 決定

GET ルートは、`Input` とリードモデルから作る文字列（検証子）を返せる。サーバは、コンパイル時に決まるビルド ID、セッションの CSRF トークン、検証子の 3 つからハッシュを作り、弱い `ETag`（`W/"…"`）として送る。`If-None-Match` が一致したら、ビューを呼ばずに 304 を返す。検証子のある応答には、ルートが別に指定しない限り `Cache-Control: private, no-cache` を付ける。

# 理由

検証子だけを ETag にすると、セッションが新しくなったときに、古いトークン入りのページが 304 で戻り、その後の POST が 403 になる。デプロイの後は、古いマークアップが出続ける。ビルド ID とトークンを混ぜれば、どちらが変わっても 200 の完全な応答になる。本文のバイト列から作った値ではないので、強い ETag とは言えない。`If-None-Match` は弱い比較で照合するので、弱い ETag でも 304 は返せる。業務アプリの画面はセッションごとに違うので、共有キャッシュ（CDN）には置けない。`private, no-cache` は、ブラウザに保存させたうえで、使う前に必ず確認させる。

# 破棄した案

- 本文のハッシュを ETag にする（描画してからでないと比べられず、描画を省けない）
- 検証子だけを強い ETag として送る
