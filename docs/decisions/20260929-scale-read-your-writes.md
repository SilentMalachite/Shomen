# 状況

Rails は読みを replica に回し、書いた直後の一定時間は同じセッションの読みを primary に向けて、古い画面を見せないようにしている。Shomen では、replica の遅れと、表に置いたプロジェクションを更新するコンシューマの遅れの 2 つがある。どちらも、POST の後のリダイレクト先で変更が見えない原因になる。

# 決定

約束は次の 1 つにする。要求がイベントを追記したら、セッションがその追記の `id` を覚えている間、同じセッションの後の要求は、どのプロセスが受けても、その追記より古い状態を見せない。

セッションは、最後に追記した `id` を覚える。置き場は仕様 6 の map（署名付きクッキーか DB）で、map の API と一緒にフェーズ 7 までに決める。覚えた `id` は一定時間（既定 60 秒）で忘れる。読む側は、読む先がその `id` に届くまで、上限つき（既定 2 秒）で待つ。

- メモリ上のプロジェクションが replica から追いつく場合: 上限までに届かなければ、primary から追いつく
- 表に置いたプロジェクションを replica で読む場合: 上限までに届かなければ primary で読む
- primary でも届かない場合（コンシューマが遅れている）: 古い状態を見せず、`Shomen::Unavailable` を投げる。捕まえられなければ 503 の HTML 文書になる

# 理由

一定時間だけ primary に向ける方法では、遅れがその時間を超えると古い画面が出る。`id` はストリームをまたいだ順序なので、どこまで追いついたかを正確に比べられる。古い状態を黙って見せるより、503 で遅れを表に出す方が、利用者が同じ操作を繰り返さずに済む。ただし、チェックポイントも覚えた `id` も全体の順序なので、1 つのイベントでコンシューマが詰まると、その後に追記したセッションは、関係の無いストリームへの追記でも待たされる。覚えた `id` を一定時間で忘れれば、503 が続くのはその時間までになる。その後は古い状態が見えうるので、約束は覚えている間に限る。詰まったコンシューマは、別に監視して直す。

# 破棄した案

- 書いた後の一定時間（Rails の設定例では 2 秒）だけ primary から読む
- replica を使わず、primary を大きくする
- 上限を過ぎたら、古い状態のまま表示する
- 覚えた `id` を忘れない（1 つのイベントが詰まると、その後のページがずっと 503 になる）
