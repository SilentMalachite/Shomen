# 状況

コンシューマと SSE は、新しいイベントが入ったことを知る必要がある。ポーリングだけでは、間隔ぶん遅れるうえに、間隔を縮めるほど DB への問い合わせが増える。フェーズ 5 の SSE は、1 プロセスの中の変更しか配れない。

# 決定

Postgres アダプタは、追記と同じトランザクションで `NOTIFY` を送る。ペイロードは新しい最大の `id` だけにする。各プロセスは `PG.connect_listen` で `LISTEN` 専用の接続を 1 本持ち、通知を受けたらコンシューマと SSE ストリームを起こす。この接続はプールに入れず、Postgres に直接つなぐ。トランザクション単位で接続を使い回すプロキシ（PgBouncer の transaction モードなど）は経由しない。

通知とは別に、一定間隔（既定 5 秒）でもポーリングする。`LISTEN` の接続が切れたら、つなぎ直してすぐに追いつく。SQLite には通知が無いので、ポーリングだけを使う。

# 理由

トランザクションの中の `NOTIFY` は、コミットしたときにだけ届く。巻き戻った追記の通知は出ない。DB 以外のサービスが要らない。ペイロードには大きさの上限があるので、イベント本体は載せず、`id` だけを載せて本体は表から読む。トランザクション単位のプロキシは、セッションを保たないので `LISTEN` が働かない。通知は接続が切れると落ちるので、ポーリングで取りこぼしを拾う。

# 破棄した案

- Redis の pub/sub を使う
- ポーリングだけにする
- 通知のペイロードにイベント本体を載せる
- プールの接続で `LISTEN` する
