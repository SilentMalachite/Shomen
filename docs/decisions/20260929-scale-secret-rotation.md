# 状況

鍵を替えると、それまでのセッションと、開いているフォームの CSRF トークンがすべて無効になる。プロセスを 1 つずつ入れ替えるデプロイでは、新旧の鍵のプロセスが同時に動く時間がある。

# 決定

`SHOMEN_SECRET_VERIFY` を設定すると、検証だけに使う 2 つ目の鍵になる。セッションクッキーの署名と CSRF トークンを、この鍵でも検証する。この鍵で通ったクッキーは、その応答で `SHOMEN_SECRET` のクッキーに出し直す。署名とトークンは常に `SHOMEN_SECRET` で作る。受け付ける 2 つ目の鍵は 1 つだけにする。`Shomen::Server.new` には `verify_secret:` で渡せる。

鍵の入れ替えは 3 回のデプロイで行う。

1. 新しい鍵を `SHOMEN_SECRET_VERIFY` に入れる
2. `SHOMEN_SECRET` と `SHOMEN_SECRET_VERIFY` を入れ替える
3. `SHOMEN_SECRET_VERIFY` を消す

手順 3 で切れるのは、手順 2 の後に一度も使われず、新しい鍵で出し直されなかったセッションと、手順 2 より前に描画されたまま送信されていないフォームである。手順 2 と 3 の間を空けるほど、切れるものは減る。

# 理由

各手順のデプロイ中、どのプロセスも、その時点でどこかのプロセスが署名に使っている鍵をすべて検証できる。手順 1 の間、署名に使われるのは古い鍵だけである。手順 2 の間は新旧両方だが、全プロセスが両方を検証する。手順 3 の間は新しい鍵だけである。そのため、どのプロセスに振り分けられても通る。変数名を「前の鍵」ではなく「検証用」にしたのは、手順 1 では新しい鍵を入れるためである。

# 破棄した案

- 変数名を `SHOMEN_SECRET_PREVIOUS` にし、1 回のデプロイで入れ替える（入れ替え中、古いプロセスが新しい鍵のクッキーを読めない）
- 検証用の鍵を複数、カンマ区切りで受け付ける
- 鍵の入れ替えは、利用者に再ログインしてもらって済ませる
