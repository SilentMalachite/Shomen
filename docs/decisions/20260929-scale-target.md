# 状況

仕様の前提は、想定利用者を「少人数または一人」としていた。ユーザーは、Rails と同じ規模で動かせるようにしたいと求めた。Rails は、1 つのアプリを多数のプロセスで横に並べ、DB の primary と replica、ジョブ、キャッシュで規模を出している。Rails の API や機能の広さを取り込むことは、仕様の範囲外（Rails 互換、ActiveRecord 的なモデル層、Devise 級の認証）に当たる。

# 決定

目標を Rails と同じ運用規模に置く。1 つのアプリを同じプロセスの集まりとしてロードバランサの後ろに並べ、Postgres の primary と replica の上で動かす。アプリは SQLite の 1 プロセスで始まり、ルート、ビュー、コマンド、イベントのコードを変えずにそこまで育つ。プロセスは、他のプロセスが必要とする状態を持たない。セッションの map も、署名付きクッキーか DB に置き、1 プロセスのメモリには置かない。DB 以外の裏側のサービス（Redis、メッセージブローカ、専用キャッシュ）は必須にしない。シャーディングと複数リージョンからの書き込みは範囲外にする。Rails 互換と機能の広さは、引き続き範囲外とする。

仕様は次のように変える。前提と範囲を `docs/en/00-INSTRUCTION.md` で改訂する。複数プロセスで読めるイベント表とプロジェクションを、フェーズ 3 より前に決める。フェーズ 6 に本番プロセスの約束を足す。フェーズ 7「scale out」を新設する。

req/s などの数値目標は置かない。計測の土台になる Store ができてから決める。

# 理由

Rails の大規模運用で先に詰まるのは、アプリサーバではなく DB とキャッシュである。Crystal は 1 プロセスあたりの処理量が大きいので、Shomen でも同じ所が上限になる。イベントは追記のみなので、イベント表の形は後から変えにくい。複数プロセス前提の形は、フェーズ 3 より前に決めるのが最も安い。Rails 8 が Solid Queue、Solid Cache、Solid Cable で DB に寄せたのと同じく、DB 1 つで足りる形にすれば、運用するサービスが増えない。

# 破棄した案

- 前提を少人数のまま残し、規模はアプリ側の工夫に任せる
- Rails の機能（ActiveRecord、ジェネレータ、ActiveJob の API）を移植する
- マイクロサービスに分けて規模を出す
- Redis を前提にして、ジョブ、キャッシュ、配信をまかなう
- 数値目標を先に決める
