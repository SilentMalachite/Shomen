# 状況

Rails は、フラグメントキャッシュで描画の負荷を下げる。Shomen の断片には、セッションごとに違う CSRF トークンや、見る人ごとに違う内容（名前、権限で絞った一覧など）が入ることがある。

# 決定

描画した断片は、プロセス内の上限つきキャッシュ（LRU）に置ける。キャッシュはプロセス内の全セッションが共有する。キーには、断片が依存するものをすべて含める。

- 断片の名前と入力
- 見る人によって中身が変わるなら、見る人
- 表示するデータとともに変わる値。1 つのストリームを表示する断片ならそのストリームの版、一覧ならプロジェクションのチェックポイント

追記があるとキーが変わるので、手で消す操作は無い。いまの要求の CSRF トークンを含む断片をキャッシュしようとすると、例外を投げる。外部のキャッシュサーバは使わない。

# 理由

全体のチェックポイントをキーにすると、どこかで追記があるたびにすべてのキーが変わり、書き込みの多いアプリではほとんど再利用されない。表示するデータに近い値ほど、長く使える。キャッシュは共有なので、見る人をキーに入れ忘れると、ある人向けの内容が別の人に出る。これはキーを決める側の責任で、フレームワークは実行時には見分けられない。CSRF トークンだけは、描画した後にトークンを含むか確かめれば機械的に止められる。トークンが共有されると、ある利用者のトークンが別の利用者に渡り、最初の利用者への CSRF が成り立つ。プロセスごとのキャッシュは台数ぶん重複するが、上限があるのでメモリは増え続けず、サービスも増えない。

# 破棄した案

- 全体のチェックポイントをキーにする
- セッションごとにキャッシュを分ける（メモリがセッション数に比例して増える）
- Solid Cache のように DB にキャッシュを置く
- Memcached や Redis を使う
- 追記のたびに、該当するキーを手で消す
