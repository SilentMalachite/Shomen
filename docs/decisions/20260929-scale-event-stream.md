# 状況

仕様 7 のイベント表の例は `events(id, type, payload, at)` だった。どの対象のイベントかを示す列が無く、同じ対象へ 2 つのプロセスが同時に書いても気づけない。イベントは追記のみなので、保存を始めた後に表の形を変えるのは難しい。

# 決定

イベントはストリームに属する。ストリームは時間とともに変わる 1 つの対象（1 人のユーザーなど）で、名前は文字列にする。表は次の形にする。Postgres では整数の列を `BIGINT` にする。

```
events(
  id      INTEGER PRIMARY KEY,
  stream  TEXT    NOT NULL,
  version INTEGER NOT NULL,
  type    TEXT    NOT NULL,
  payload TEXT    NOT NULL,
  at      TEXT    NOT NULL,
  UNIQUE (stream, version)
)
```

`version` はストリームごとに 1 から数え、欠けを作らない。追記は、ストリームがいまどの版にあると期待するかを渡す。ストアは、同じトランザクションの中でストリームの最大の `version` を読み、期待した版と等しいときだけ、続きの版で挿入する。等しくなければ、古くても先走っていても何も書かず、`Shomen::Conflict` を投げる。UNIQUE 制約は、この確認をすり抜けた競合を止める最後の砦にする。ストアは再試行しない。ルートが捕まえなければ、サーバは 409 の HTML 文書を返す。`payload` は JSON、`at` は UTC の RFC 3339 にする。

# 理由

楽観的排他は、ロックを持たずに同時書き込みを検出できる。UNIQUE 制約だけでは、期待した版が古い場合しか止められない。先走った版で挿入すると、行を書き換えないので、その欠けは二度と埋まらない。追記は SQLite では `BEGIN IMMEDIATE`、Postgres ではアドバイザリロックで直列になるので、確認と挿入を同じトランザクションで行えば競合しない。409 は、フェーズ 2 の 422 と同じく、利用者に見せる HTML にできる。ストアが自動で再試行すると、コマンドが古い状態で判断した結果をそのまま書いてしまう。

# 破棄した案

- 表を仕様の例のままにし、同時に書いたら後の書き手を勝たせる
- UNIQUE 制約だけで衝突を検出する
- 追記の前にストリームを行ロックする悲観的排他
- 衝突したらストアが自動で再試行する
