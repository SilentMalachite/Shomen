# 状況

チェックポイント方式（`20260929-scale-projection-checkpoint.md`）は、`id` N まで読んだ読み手が、後から N 以下の新しいイベントを見つけないことを前提にする。SQLite は書き手が 1 つなので、これを満たす。Postgres の identity 列は、採番した順にコミットされるとは限らない。

# 決定

Postgres アダプタは、次の 3 つを守る（フェーズ 6）。

- `events` へのすべての追記は、挿入（採番）の前に、固定の 1 つのキーで `pg_advisory_xact_lock` を取る
- ロックを取ったら、挿入してすぐにコミットする。コンシューマが反応として追記するときも、バッチの最後に行う
- `id` の identity は `CACHE 1` にする

# 理由

10 番より先に 11 番がコミットされると、11 まで読んだ読み手は、後から見えるようになった 10 を飛ばす。採番の前に同じキーでロックを取れば、採番からコミットまでが直列になり、この欠けは起きない。コミットはロックが外れる前に見えるようになる。sequence がセッションごとに番号をまとめて確保すると、直列でも順序が崩れるので、`CACHE 1` にする。

代わりに、追記の上限はおおよそ「コミット 1 回の待ち時間につき 1 回」になる。コミットの待ちが 1〜2 ms なら毎秒数百〜千回ほどで、同期 replica の応答を待つ構成ではさらに下がる。1 回の追記で複数のイベントを書けば、1 回のコミットにまとまる。業務アプリの書き込み量ならこれで足りる。足りなくなったら、トランザクション ID による方式を検討する。

# 破棄した案

- Postgres のトランザクション ID（`xid8` と `pg_snapshot_xmin`）で見える順を判定する。直列にしないぶん速いが、SQLite と意味をそろえにくい
- 読み手は一定時間より新しいイベントを読まず、遅れてコミットされる分を待つ
- 順序の保証をせず、読み手が欠けた `id` を後から探す
