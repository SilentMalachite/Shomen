# 状況

サーバはシグナルを扱っていないので、SIGTERM を受けると処理中の要求を待たずに終了する。プロセスを 1 つずつ入れ替えるデプロイでは、そのたびに要求が途中で切れる。

標準の `HTTP::Server#close` は、フラグを立てるだけである。フラグは要求を読むループの先頭で確かめられる（Crystal 1.21 の `http/server/request_processor.cr`）。待機中のキープアライブ接続は次の要求を読むところで止まっていて、その要求をもう 1 つ処理してしまう。処理中の応答は `Connection: keep-alive` を送ってしまう。`listen` から戻った後に main が終わると、処理中のファイバーも止まる。

# 決定

SIGTERM と SIGINT を受けたら、次の順に進める。

1. `HTTP::Server#close` で新しい接続を受けるのをやめる
2. 処理中の要求の数を数え、合図の後に書く応答には `Connection: close` を付ける
3. 要求を処理していない接続を閉じる
4. SSE の接続は、上限を待たずに閉じる
5. 処理中の要求が 0 になるか、`start` の引数 `shutdown_timeout`（既定 25 秒）を過ぎたら、終了コード 0 で終わる

# 理由

`close` だけでは、キープアライブ接続の扱いのせいで、待ちがいつも上限まで延びる。そのうえ、ロードバランサが使い回す接続を終了時に切ってしまう。処理中の数を自分で数え、`Connection: close` で再利用をやめさせれば、要求が済みしだい終われる。Kubernetes は、既定で SIGTERM の 30 秒後に SIGKILL を送るので、既定の上限はその内側に置いた。`docker stop` の既定は 10 秒なので、Docker では `shutdown_timeout` を下げるか、停止の猶予を延ばす。SSE は長く続く接続なので待つ対象から外し、クライアントの再接続に任せる。

# 破棄した案

- 終了の合図で即座に終わり、落ちた要求はロードバランサの再試行に任せる（POST は再試行できない）
- `HTTP::Server#close` だけに任せる
- 待つ上限を設けない
