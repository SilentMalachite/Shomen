# 状況

`20260929-scale-read-your-writes.md` は、セッションが最後に追記した `id` を一定時間（既定 60 秒）覚え、その間の同じセッションの要求がその追記より古い状態を見せないと決めた。2026-10-01 にユーザーは、`id` を既存の `shomen_session` とは別の署名付きクッキーに置き、ルートが任意の値を書く汎用の map API はまだ作らないと決めた（`docs/superpowers/plans/2026-10-01-phase7-overview.md`）。サーバが「この要求で追記した `id`」を知る方法、クッキーの形、ルートが「見る必要のある `id`」を得る方法は決めていない。`20260929-phase3-store-api.md` は、`append` が最後の `id` を返すかをここで決めると先送りした。

# 決定

- `Shomen::Store#append` は追記した最後のイベントの `id` を返す（`Int64`）。空の配列なら何も追記せず 0 を返す
- `Shomen::Route#remember(id : Int64) : Nil` は、この応答の後、セッションに `id` を覚えさせる。0 以下は何もしない。追記した要求のルートが `remember store.append(...)` と書く
- `Shomen::Route#must_see : Int64` は、この要求が見せてよい最も古い状態の `id`。セッションが覚えている `id` で始まり、0 は覚えていないこと。`remember` は、より大きければそれに上げる。ルートはこれを `projection.catch_up(must_see)` と `consumer.read(must_see) { … }` に渡す。渡し忘れたルートは待たない
- ルートの `handle` は、`remember` が呼ばれていれば、応答の `Shomen::Response#remember` にそのときの `must_see` を入れる。サーバは `remember` が 0 より大きい応答に、クッキー `shomen_append` を付ける。例外で終わった要求（409、503 など）は何も覚えない
- `shomen_append` の値は `<id>.<期限>.<署名>`。期限は覚えた時刻に 60 秒（`Shomen::Session::REMEMBER`）を足した Unix 秒。署名は `SHOMEN_SECRET` を鍵にした `"append:" + セッションの id + "." + id + "." + 期限` の HMAC-SHA256 の 16 進。属性は `shomen_session` と同じ（Path=/、HttpOnly、SameSite=Lax、HTTPS なら Secure）で、`Max-Age=60` を付ける
- `Shomen::SessionStore#load` は、署名が `SHOMEN_SECRET` か `SHOMEN_SECRET_VERIFY` で合い、期限の前で、同じセッションに結びついた `shomen_append` の `id` を `Shomen::Session#remembered` にする。それ以外（無い、形が壊れている、署名が合わない、期限を過ぎた、別のセッション）は 0。`SHOMEN_SECRET_VERIFY` で通っても出し直さない
- SSE は、追記で起きて断片を描き直す前に、ルートの `must_see` を起こした追記の `id` に上げる。断片のブロックが `catch_up(must_see)` と書けば、replica が遅れていても、起きた追記より古い断片を送らない
- 描き直しが `Shomen::Unavailable` を投げたら（断片が遅れたコンシューマを `read(must_see)` で読んだ）、SSE は何も送らず、待っている `id` を進めずに 200 ミリ秒（`Shomen::SSE::RETRY`）後に描き直す。ストリームは切らず、ハートビートは続ける
- 覚える時間は設定できない。必要になったら引数を足す

# 理由

ルートは追記した Store と、追記した `id` の意味を知っている。`append` が `id` を返し、ルートが `remember` で渡せば、Store はセッションを知らず、サーバは Store を知らないまま（アーキテクチャのモジュール境界）、サーバがクッキーを書ける。要求ごとの文脈に Store が書く案は、Store がサーバの要求を知るか、ファイバーに結びついた隠れた状態が要る。`must_see` は `remember` で上がるので、追記した要求がそのまま描画しても、その追記を見る。

署名にセッションの `id` を入れるので、別のセッションのクッキーを写しても通らず、新しいセッションは古い `id` を引き継がない。期限を値に入れて署名するので、`Max-Age` を無視するクライアントでも 60 秒で忘れる。値は 60 秒で消えるので、鍵の入れ替えで出し直す必要は無い。覚えた `id` を偽っても、その利用者のページが待つか 503 になるだけで、ほかのセッションには届かない。

同じセッションの 2 つの要求が同時に追記すると、後に届いた応答のクッキーが残る。先に追記した要求の応答が後に届けば、セッションは小さい方の `id` を覚え、次のページが後の追記を見ないことがある。クッキーの値は 1 つで、書くときに比べられないからで、約束は 1 つずつ送られる要求の間に限る。

SSE は同じ要求の中で何度も描き直す。描き直しのたびに起きた追記の `id` を `must_see` にすれば、replica を使うアプリでも、ルートの書き方を変えずに最新の断片を送れる。遅れたコンシューマで描けないときにストリームを切ると、ブラウザがつなぎ直すまで更新が止まり、サーバのログに未処理の例外が残る。待っている `id` を進めなければ、次の試みで同じ追記をもう一度描く。間隔を置くのは、すぐに `Shomen::Unavailable` を投げる断片で CPU を回し続けないためである。

# 破棄した案

- 要求ごとの文脈（ファイバーに結びついた表）に Store が追記の `id` を書き、サーバが読む（Store とサーバの境界を越える隠れた状態）
- ルートに Store を渡す `append` ヘルパを足し、ヘルパが覚える（ルートが Store を知る。コマンドの結果を扱う書き方が 2 つになる）
- `shomen_session` の値に `id` を足す（セッションのクッキーが要求のたびに変わる。仕様 6 の map を先に作ることになる）
- 汎用の map API（ユーザーが先送りした）
- 期限を `Max-Age` だけで表す（クライアントがクッキーを持ち続けられる）
- `SHOMEN_SECRET_VERIFY` で通った `shomen_append` を出し直す（60 秒で消える値に出し直しは要らない）
