# 状況

フェーズ 2 は「CSRF トークンが一致しない POST は 403」としている。ほかのメソッドとフィールド名は書いていない。

# 決定

POST、PUT、PATCH、DELETE を検査する。GET と HEAD は検査しない。トークンは urlencoded の本文にあるフィールド `_csrf` から読み、セッションの `id` から導いたトークン（`20260929-phase2-session-store.md`）と `Crypto::Subtle.constant_time_compare` で比べる。本文が urlencoded でなければフォームは空とみなし、403 にする。検査はルート照合より前に行うので、トークンの無い POST は、宛先のパスが無くても 403 になる。403 は `Shomen::Forbidden` の例外ではなく、`Server` が直接返す HTML 文書である。ルートが自分で拒否したいときに使う `Shomen::Forbidden` も置き、`Server` が 403 に変換する。

# 理由

ほかの unsafe method を検査しない理由が無い。フェーズ 4 の fetch が使うヘッダでのトークン受け渡しは、そのフェーズで決める。03-CONVENTIONS は、想定内の 4xx を Response として返すとしている。

# 破棄した案

- POST だけを検査する
- 照合してから検査し、未知パスへの POST を 404 にする
- `X-CSRF-Token` ヘッダをフェーズ 2 で受ける
